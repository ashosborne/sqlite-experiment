# wal-002 — Checkpoint modes

Slice: `wal` · Status: `documented` · Confidence: `observed-in-code` · Card written: 2026-08-11T10:29:07Z
As-is behaviour card (Discovery v0.2 Phase B). Not a redesign, not a user story.

## Summary

Four checkpoint modes differing in blocking and wal-reset behaviour.

## Entrypoints (citations)

- `sqlite3WalCheckpoint()` (other) — `src/wal.c:4301`, `src/wal.c:2199`

## Inputs / outputs / observables

- Checkpoint mode effects: PASSIVE (best-effort, never blocks), FULL (waits for readers), RESTART (also resets wal), TRUNCATE (resets + truncates file); returned (nLog,nCkpt) counts

## Behaviour (as implemented)

- sqlite3WalCheckpoint (src/wal.c:4301) → walCheckpoint (src/wal.c:2199): copies committed frames up to the reader-safe boundary back into the db file, then per-mode wal reset/truncate; auto-checkpoint via wal_autocheckpoint (default 1000 pages) runs PASSIVE

## Validation rules found in code

- Busy handler used in blocking modes; SQLITE_BUSY when blocked in FULL/RESTART/TRUNCATE

## Edge cases found in code

- PASSIVE can leave a partially-checkpointed wal (backfill watermark)
